## 1. 平台

- **名字和位置（已定，11-05）：**
  - 平台叫 rnl-hub，正式仓库是 `rich-netlist/rnl-hub`。
  - 开发仓库是 `many-question/rnl-hub-dev`，本地在 `D:/repositories/rnl-hub-dev`，后续的全部开发事项和文件都放在这里。
- **和 Mega Precision 无关（已定，11-05）。**
  - 草稿里以 mega-precision 为中心的安排不再适用，例如"mega-precision 是根 IP""R01–R10 作为首批参与者"。
  - 第一批加入的很可能是一些更简单的试点 IP；R01–R10 以后再说。
- **公开（已定，11-04）。** 单仓库，所有 IP 都放在 `design/<IP>/` 下。
- **所有东西都是 IP（已定，11-04）。** 每个 IP 有唯一的定义；实现可以有多组版本树；引用写到具体版本。
- **提交后不能原地修改，只能出新版本（已定，11-03）。**
- **网表用 RNL，不带 PDK 数据（已定，11-04）。** 参与者在自己的环境里设计和仿真。
- **网站（已定，11-03/04）：** CI 自动构建网站，网站用 RNL 查看器直接看设计。查看器如果成为瓶颈，以后可能专门建站托管。

## 2. 对象

### 2.1 IP 定义

- **一律在平台上（已定，11-05）。**
- **只有三项：名字、描述、IO（已定，11-05）。** 相当于一个子电路头的定义信息。工艺和指标都不在定义里。

### 2.2 实现

- **工艺是实现的属性（已定，11-05）。** 同一个 IP 可以有不同工艺的实现；行为模型也可以看成一种"工艺"。
- **两个字段（已定，11-05）：**
  - 实现类型：VA 模型、理想模型、RTL、晶体管级、混合等；
  - 工艺信息：可以为空。
- **VA 和数字模块都只是实现（已定，11-05）。** VA 没有特殊之处；数字模块（如 Verilog）也可以收录。混合仿真怎么跑，以后再说。
- **组合（已定，按建议，11-05）：** 引用了别的 IP 的实现就是组合，要固定所引用 IP 的版本。电路实现也可以引用别的 IP。
- **新 IP 不强制带 VA 模型（已定，按建议，11-05）。** 只建议带一个快速的行为级实现，方便上层组合做系统仿真。
- **对子 IP 的要求（已定，按建议，11-05）：**
  - 组合只声明对子 IP 的指标要求，按 `<tb 组>.<指标>` 写。
  - 参数化的实现照常在网表里传实例参数，不需要特殊机制。
  - 草稿里"给固定到 VA 模型的子 IP 注入预算参数"的机制取消。
- **版本树和改进关系（已定，按建议，11-05）：**
  - 一个实现组是一个账号的一条版本链，只有组作者能往后加版本。
  - 改进别人的实现时，开一个新组，`based_on` 写明基于哪个版本。`based_on` 必填，从零开始的写空列表。
  - CI 拿新实现和已有实现比较：完全相同的文件按哈希比，网表按结构相似度比。很相似却没声明的，标"疑似未声明来源"，交给人看，不阻止合并。
  - 网站把所有组按 `based_on` 连成一棵树。
- **分叉前不强制先提 issue（已定，按建议，11-05）。** 只作为规范：想改进别人的实现，最好先提 issue。

### 2.3 tb

- **tb 是 IP 下面的一种贡献（已定，11-05）：**
  - 同一个 IP 可以有很多 tb，每个 tb 对应一组指标的定义。
  - tb 和设计一样有自己的版本树；验证时必须指明具体的 tb 版本。
  - 谁都可以写 tb，人或 agent 都行，在 `author` 里写清楚，不强求。
- **tb 的内容（已定，11-05）：** 仿真网表、仿真命令行，以及分析代码（从仿真结果文件算出声明的指标）。代码不限，建议用 Python。
- **指标只在 tb 里定义（已定，按建议，11-05）：**
  - 每个 tb 在 `tb.yaml` 里列出它的指标：名字、单位、好坏方向、复现容差、说明。
  - 指标的全名是 `<tb 组>.<指标>`，例如 `tb_static.inl`。同一个 tb 组里，一个指标名的含义不能变；含义变了就换名字。
  - 目标值、组合对子 IP 的要求，都按全名写。
  - 几个 tb 测同一个量（例如口径不同的两个 THD）时，网站按 tb 分开列，不合并。
- **目录和格式（已定，按建议，11-05）：** 见第 3 节。
- **分析代码的运行（已定，按建议，11-05）：**
  - CI 从不运行分析代码。
  - 平台工具在单独的进程和临时目录里运行分析代码，默认不联网。
  - 第一次运行某个 tb 版本前，先显示代码，以及它和上一版的差异。
  - 建议验证者用容器运行。
  - lock 记下分析代码和依赖文件的哈希，复现必须用同一份代码。

### 2.4 验证

- **实现和验证是两个层面（已定，11-05）。** 可以只提交实现、不提交自己的验证，虽然不建议。
- **一种记录（已定，按建议，11-05）：** 不再区分"结果"和"验证"。每次有人跑 tb，就提交一条验证记录，内容是：
  - 被测实现的版本；
  - 跑了哪些 tb 的哪个版本；
  - 展开树里全部 IP 的版本（`lock.json`）；
  - 环境声明、各指标的数值和关键证据。
- **来源和配置（已定，11-05）：** 每条记录都要声明仿真器版本、设置，甚至关键的系统信息。仿真器不统一。格式见第 3 节。
- **复现与可信度（已定，11-03/04；按建议，11-05）：**
  - 同一个实现、同一组 tb 版本、同一个 lock 的多条记录，就是互相的复现。
  - 网站按 tb 里每个指标的容差判断是否一致。"已验证"的意思是：来自 n 个不同账号的记录一致。
  - 第一条记录不再特殊。独立性按账号计算。
  - 两条记录的仿真器或 PDK 发行版不同时，网站标"跨环境"。
- **放在一个目录（已定，11-05）：**
  - 目录是 `design/<IP>/verifications/<yyyy-mm>/<UTC>-<短名>/`，里面放 `verification.yaml`、`lock.json` 和 `evidence/`。
  - 不鼓励放原始数据，只放关键证据，例如画结果图用的数据。
- **一次仿真里，同一个 IP 只能用一个版本（已定，11-05）。** 两个版本就是同名子电路的两份定义，仿真会报错。
- **实现和验证的 PR 都要声明所引用的 IP 版本（已定，11-05）。**
- **记录编号（已定，按建议，11-05）：** `<UTC>-<短名>`。账号不写进文件；撞号时合并队列会挡住后一个。

### 2.5 CI

- **只查格式和规则，不验证数据（已定，11-03）。**
- **卫生检查（已定，11-05；细节待细化）：** 器件名不是保密信息。CI 只查：
  - 没有 PDK 模型文件或模型卡内容；
  - 没有工艺库的 include 语句；
  - 没有本机路径、主机名、用户名和密钥样式的字符串。
- **工艺登记（已定，按建议，11-05）：** 只写名字和说明，以及常用的角名供 tb 参考；器件名单可选，不用来做检查。

## 3. 格式要点（已定，按建议，11-05）

### 3.1 tb

```text
design/<IP>/tb/<tb 组>/v<n>/
  tb.yaml            指标、工况、仿真命令、分析入口、依赖
  tb.scs             仿真网表（RNL）
  analyze.py         分析代码：读仿真结果目录，输出指标和证据
  requirements.txt   Python 依赖，写死版本
  README.md          声明和说明
```

```yaml
schema: hub/tb/1
author: <署名>
patents: waived
metrics:
  - {id: inl, unit: LSB, better: lower, tol: {abs: 0.05}, desc: 端点拟合的积分非线性，取最大绝对值}
  - {id: dnl, unit: LSB, better: lower, tol: {abs: 0.05}}
simulator: {name: spectre}             # 这个 tb 写给哪种仿真器；验证时声明实际用的
run: "spectre tb.scs +aps -format psfascii -raw out"
analyze: {entry: analyze.py, python: ">=3.10", requirements: requirements.txt}
cases:
  tt_nom: {corner: tt, temp: 27, supply: 1.0}
```

- **地址：** `<IP>:<tb 组>/v<n>`。
- **分析代码的约定：** `analyze.py <仿真结果目录> <输出目录>`，输出 `metrics.json`（每个工况、每个指标一个数）和证据文件。

### 3.2 环境声明

```yaml
env:
  simulator: {name: spectre, version: "23.1.0.123", command: "spectre tb.scs +aps ...", options: {reltol: 1e-6}}
  pdk: {process: <工艺名>, release: <发行名>}       # 用到工艺时才写
  analysis: {python: "3.11.6", packages: {numpy: "1.26.4", scipy: "1.11.4"}}
  system: {os: "RHEL 8.6", cpu: "Xeon Gold 6338", threads: 16}
  note: <自由文本>
```

CI 只查格式，以及不含本机路径、主机名、用户名和密钥样式的字符串。

### 3.3 改名

- **工具：** 草稿里的命令行工具 `mpflow` 改叫 `hubflow`。
- **格式标识：** 格式前缀从 `mp/<类型>/<n>` 改成 `hub/<类型>/<n>`。

## 4. 外部实现、许可证与专利

- **引用的是实现，不是定义（已定，11-05）。** 定义一律在平台上。
- **许可证（已定，11-05）：** 全平台只用两种：
  - 实现和 tb 用 CERN-OHL-P-2.0；
  - 其余全部用 MIT：定义文本、目标值、验证记录、证据、笔记、格式 schema、工具。
- **外部实现（已定，11-05）：**
  - 原许可证是 CERN-OHL-P-2.0 的，自动收录；
  - 其他许可证的只引用，按原许可证，平台列出每个实现的许可证要求；
  - 不存副本；没有许可证的不收；
  - 第一版只收 GitHub 公开仓库。
- **认领（已定，按建议，11-05）：** 先不做。原作者可以开自己的组，`based_on` 指向登记者提交的版本。
- **专利（已定，11-05）：**
  - 向平台提交的全部内容都放弃专利权。
  - 不愿放弃的，不进收录，只能留作引用，并声明专利信息。
  - 贡献说明里要着重强调这一点。
  - 落实办法：CERN-OHL-P-2.0 第 6.1 条的专利许可；文件里写 `patents: waived`；`CONTRIBUTING.md` 第一节，草稿见 `drafts/66_framework_spec.md` 10.3 节。

## 5. 身份与署名

- **账号由 CI 从 PR 自动取，不写进文件（已定，11-05）。**
- **署名（已定，11-05）：** 文件里只有一个可选的自由文本字段 `author`，真人和 agent 都可以署名。贡献说明建议 agent 写成 `<agent 名>(<模型名>)`，但不强制，因为有人不想公开所用的模型。
- **列表（已定，11-05）：** 实现列表同时列出署名和账号。
- **不需要参与者登记（已定，11-05）。**

## 6. 协作与网站

- **PR 和 issue（已定，11-04）：** 公开在同一个仓库。CI 按规则检查和分类，打上 `ip/<IP>` 等标签。
- **过滤和订阅（已定，11-04）：** 按 IP 过滤 issue 和 PR 靠标签；按 IP 订阅只用网站的 Atom 订阅源。
- **PR 的形状（已定，按建议，11-05）：**
  - 一个 PR 只涉及一个 IP。例外是组合可以带上它新建的子 IP。
  - 新 IP 的定义可以单独提交，也可以和它的第一个实现、tb 一起提交。
  - 验证记录可以单独提交，也可以和实现一起提交。
- **合并（已定，按建议，11-05）：** 用合并队列和 squash 合并。合并前队列会按最新的 `main` 重新检查，一个 PR 对应一个提交。
- **网站构建（已定，11-05；做法按建议）：**
  - 增量构建，两次构建之间至少隔半小时。
  - `site` 工作流每 30 分钟检查一次 `main` 有没有新合并：有就构建，没有就跳过；也可以手动触发。
  - GitHub 的定时任务可能推迟，所以能保证"至少隔半小时"，不能保证"半小时内一定更新"。
  - 增量状态放在已发布网站的 `index/state.json` 里。
- **排序和展示门槛（已定，按建议，11-05）：** 先用草稿 64 号文档 9.2 节的默认规则，试运行后再修订。
- **大小上限等（已定，11-04）：**
  - 单个网表不超过 1 MB，每个实现不超过 2 MB，每条验证记录不超过 256 KB；
  - 验证可以替换实例的版本；
  - 网站现场抓取网表。
  - 草稿里关于组织和套餐的建议，已经被 rich-netlist 组织取代。

## 7. 建议（待确认）

### B12 实现类型和工艺的取值

- **`type`：** 取值建议为
  - `ideal`：理想元件搭的模型；
  - `va`：VA 行为模型；
  - `rtl`：Verilog 等 RTL；
  - `transistor`：晶体管级；
  - `composition`：只由子 IP 组成；
  - `mixed`：以上几种混在一起。

  取值表放在 `tools/` 里，以后可以增加。
- **`process`：** 写工艺登记里的名字，可以为空。`transistor` 必须写，其他类型可以不写。
- **重复提示：** 网站用来提示"疑似重复 IP"的接口指纹，只看 IO：端口的种类、方向和宽度，不看名字。

### B13 tb 的工况和工艺

- **问题：** tb 属于 IP，不属于某个工艺，但工况里有角名，同一个 tb 可能要跑在不同工艺的实现上。
- **建议：**
  - tb 只写通用角名（tt、ss、ff、sf、fs），验证时由本地绑定映射到实际工艺。
  - 行为模型和理想模型不看角名。
  - 只适用于某个工艺的 tb，在 `tb.yaml` 里写 `process`。
