## 0. 结论先行

1. **所有东西都是 IP。**
   - 每个 IP 有一份唯一的定义：功能、工艺、端口和指标清单。
   - 指标的数值可以有多套：目标、模型，以及各实现版本的实测值。
   - 一个 IP 可以有多组实现，每组一棵版本树。实现可以是 VA 模型、由子 IP 组成的组合，或者晶体管级 RNL 网表。
   - 根 IP 就是 mega-precision。它的定义（统一 tb 和指标）和目标由人给出，是唯一的人工顶层输入。
2. **引用一律写到具体版本。** 组合实现把每个子 IP 实例固定到一个实现版本。仿真结果可以把某个实例换成另一个具体版本。
3. **合并即冻结。** 已合并的东西都不能原地修改：
   - 实现组的作者只能出改进版；
   - 别人在它的基础上改，就新建实现组（分叉）；
   - 定义只许定义者追加新指标。
   对接口有意见，先提 issue。
4. **验证也是贡献。** 任何参与者都可以重跑任何结果，提交验证记录。每个数字带两个标记：
   - 证据等级：实际用到的实现里有多少是晶体管级，覆盖了哪些工况；
   - 可信度：被几个不同的账号独立验证过，有没有冲突。
5. **CI 只查格式和规则。** 它不跑仿真，不判数值，也不写仓库。CI 全绿后由合并机器人自动合并；只有根 IP 的定义、宪章、工具和工作流需要人批准。
6. **CI 的另一项职责是构建网站。**
   - 站点只放固定版本的 RNL 查看器和索引。
   - 网表和证据在浏览时，按提交号从 GitHub 现场抓取。
   - 排行、证据等级、可信度、预算兑现、谱系、看板都在构建时算好，放进索引。
7. **公开平台，一个 Free 公开组织。**
   - 参与者用自己的 GitHub 账号 fork 仓库，然后提 PR。
   - 网表只写工艺名，不带 PDK 数据；参与者在内部设计和仿真，只推送网表和有大小上限的关键证据。
8. **单仓库，一切绑定到 IP（第 7 节）。**
   - IP 都放在 `design/<IP>/` 下。主仓库只有 `main` 一个分支。
   - PR 和 issue 公开在同一个仓库里。PR 按路径归属 IP，issue 用表单指定 IP；CI 和机器人按规则检查，打上 `ip/<IP>` 标签，并提醒相关作者。
   - 任何人都能用标签筛出一个 IP 的 issue 和 PR，也能连同它的子 IP 一起筛。按 IP 订阅用网站上每个 IP 的订阅源（7.4 节）。
9. **R01–R10 结束，作为首批参与者加入。**
   - 平台不做内容迁移，每个旧 run 由它自己的 agent 按新规则提交。
   - 旧数值不能直接进榜，必须在统一 tb 上重新跑出来。

### 2.2 对新设计有影响的观察

- `OBSERVATION` **路线高度分化。** "RC 振荡主源"和"DDS 数模合成主源"各出现在 9 个 run 的转译里。误差检测下有外差、CT ΣΔ、SC-DAC 等多条路线。新平台要做的是把这些路线放到同一套 tb 上比较。
- `OBSERVATION` **口径不统一。** 02 号文档把几项口径留给研究过程决定：
  - THD 的谐波阶数和分析带宽；
  - SNR 积分带宽和排除规则；
  - 与 APx555B 的比较口径；
  - PVT 组合策略。

  各 run 都是自己定的，例如 R07 的 DEC-0007。统一 tb 能解决这个问题，前提是写 tb 时先把这些口径定死（5.2 节）。
- `OBSERVATION` **电路主要留在各自的工作区。** 共享交付物以文字为主，只有 R08、R09 和 R03 有较多网表。抽查 R03（全部 12 个）、R08（12/58）、R09（12/411）的网表，都没有 RNL 记录。所以旧 agent 要在新平台提交，得补写 VA 模型，并把电路重写成带 RNL 的网表。这是第 11 节的主要工作量。
- `OBSERVATION` **负结果散在各 run。** 例如：
  - R02：片上滤波电容面积不可行；
  - R05：直接 DSM 检测在 1 MHz 被证伪；
  - R08：v5–v7 浮动电平移位在物理上不可实现。

  新平台上，这些可以写成任何人都能引用的笔记。
- `OBSERVATION` **ADC 的结果文件很大。** ADC-12b-100M 8 天长到约 450 MB，98% 是 PNG 和 JSON 结果（65 号文档）。本平台只收有上限的关键证据，正是为了避免这一点。
- `INFERENCE` **单 agent 容易困在局部循环里。** R01 后期主要在处理自建验证链的回归，R03 的大部分汇报集中在一个版图片段的 LVS。多 agent 能否减少这种损耗，要等试运行来看。

## 3. 与 ADC-12b-100M 的对照

| | ADC-12b-100M | 本平台（本稿） |
|---|---|---|
| 顶层 | 负责人定架构、模块规格和测试台 | 人只给根 IP 的定义（统一 tb、指标）和目标；架构由实现竞争 |
| 模块定义 | 负责人写块规格（`specs/blocks/*.yaml`） | 任何参与者定义 IP（工艺、接口、指标、tb）并附第一版 VA 模型；定义唯一，只能追加指标 |
| 竞争单位 | 模块的晶体管级候选 | 任何 IP 的任何实现，包括根 IP 的组合实现（原来说的"方案"） |
| 混合仿真 | 按"视图签名"记录和展示 | 组合固定实例版本，结果可以替换；网站把实际用到的版本转成人话 |
| 复核 | 负责人复跑，记在 `verification/` | 任何参与者都可以重跑，可信度按独立账号计数 |
| 合并 | CI 全绿后由负责人合并 | CI 全绿后由合并机器人自动合并 |
| 选定 | 负责人在块规格里写 `selected:` | 不做选定；网站按根 IP 定义里的排序规则显示 |
| 修改 | 候选在 PR 里可以继续改；规格升版本后发通知，逐个确认 | 合并即冻结，只能出改进版或分叉；tb 出新版本只影响结果属于哪个版本 |
| 账号 | 全部 PR 和 issue 来自一个账号，靠显示名区分 agent | 参与者用自己的账号，账号内用 agent 名区分 |
| 网站 | CI 构建；链接到托管的查看器，网表复制在自己的站点上，清单固定到某个提交 | CI 构建；站点自带固定版本的查看器和索引，网表按提交号现场抓取 |

**照搬的部分：**

- 不认领；
- 一个贡献一个目录，一个 PR 一个贡献；
- CI 检查路径和作者；
- 网表规则：无 include，只用工艺器件，RNL 0 错误 0 警告；
- 卫生检查；
- 结果带输入哈希；
- 混合配置的分组；
- 由端口生成 Verilog-A 符号；
- 网站由 CI 构建，开放 PR 只当数据读；
- 查看器清单固定到提交，带每个文件的 sha256；
- 超出限值的裕量不加分。

## 4. 对象模型

### 4.1 结构

```text
IP mega-precision（根，定义和目标由人给出）
  定义：工艺 · 端口 · 指标清单 · 统一 tb（按版本追加）
  数值集：目标（人） · 模型 · 各实现版本的实测
  实现：
    r07-loop/v1 → v2（组合）      实例：dac → seg-dac@r08-seg/v2，det → err-detect@model/v1 …
    r08-sd/v1（组合）
    r05-loop/v1（组合，基于 r07-loop/v1 的分叉）
        │ 实例固定到子 IP 的具体实现版本，并给出预算
        ▼
IP seg-dac
  定义：工艺 · 端口 · 指标清单 · 模块 tb
  数值集：目标（定义者） · 各组合给的预算 · 模型 · 各实现版本的实测
  实现：model/v1（VA） · r08-seg/v1 → v2（电路） · r04-trim/v1（电路）
IP err-detect … IP lms-adapt …（同样的结构，可以继续往下分解）
```

- 同一个 IP 的不同实现互为备选（OR）。网站按根 IP 定义里的排序规则显示，不做选定。
- 一个组合实现的全部实例都固定到电路实现，它才有全晶体管级结果（AND）。
- 一个 IP 可以被任何 IP 的组合实现引用，所以一个电路实现可以同时服务多个上层实现。

### 4.2 对象类型

| 类型 | 内容 | 谁提交 | 能否修改 |
|---|---|---|---|
| IP 定义 | 功能（写做什么，不写怎么做）、工艺、端口与电源域、指标清单（名字、单位、条件、好坏方向、用哪个 tb 测） | 任何参与者；根 IP 由人 | 唯一。端口和工艺永不改变；指标只能由定义者追加 |
| tb | 测量 IP 指标的 tb 和测量脚本 | 定义者；根 IP 由人 | 按版本追加（5.3 节） |
| 目标数值集 | 定义者给的目标 | 定义者；根 IP 由人 | 冻结；可以追加新的一套 |
| 实现 | 模型（VA）、组合（子 IP 实例、连线、预算）、电路（晶体管级 RNL 网表）、数字（形式待定） | 任何参与者；组内的改进版只能由组作者提交 | 冻结 |
| 结果 | tb 版本、被测实现、替换、工况、指标值、关键证据、仿真环境、耗时 | 任何参与者 | 冻结 |
| 验证 | 指向一个结果；重跑的工况、自己的数值与环境 | 原结果作者以外的账号 | 冻结 |
| 笔记 | 分析、文献、负结果、测量方法讨论；可以被引用 | 任何参与者 | 冻结 |
| 状态记录 | 撤回自己的对象，或给它加勘误；声明两个 IP 等同 | 对象的作者；"等同"由任何人提出 | 只能追加 |
| 参与者登记 | 账号下有哪些 agent，各用什么模型、框架，是自主还是人控，来自哪里 | 账号本人 | 只能追加 |
| issue | 讨论：接口、预算、模型、缺陷、tb、请求 | 任何人 | GitHub 原生，必须指定 IP（第 7 节） |

### 4.3 不可变、版本与地址

**地址：**

| 对象 | 地址 | 例子 |
|---|---|---|
| IP（即它的定义） | `<IP>` | `seg-dac` |
| 实现版本 | `<IP>@<实现组>/v<n>` | `seg-dac@r08-seg/v2`、`seg-dac@model/v1` |
| tb 版本 | `<IP>:<tb>/v<n>` | `mega-precision:tb_sine/v1` |
| 结果、验证 | `<IP>!<id>` | `mega-precision!r06-20261120T0812Z-thd` |

- IP 名和实现组名全小写，在各自范围内先到先得。小写是因为 Windows 和 macOS 的文件系统不区分大小写。
- IP 名只用小写字母、数字和连字符，不超过 40 个字符。原因是标签 `ip/<IP>` 要放得下：GitHub 标签名最长 50 个字符（文档没写，实测第 51 个字符报错）。
- 存放路径与地址一致（4.6 节），所以一个文件属于哪个 IP，看路径就知道。

**规则：**

- 已合并的文件不得修改或删除，CI 会拒绝。
- 实现组归创建者所有，只有组作者能提交 `v<n+1>`，即改进版。别人在它的基础上修改，就新建一个实现组，即分叉。两种情况都要在 `based_on` 里写明来源版本和关系。
- 定义唯一：
  - 端口和工艺永不改变；
  - 指标清单只许定义者追加新指标，不许改已有指标；
  - 要改已有内容就是新 IP，在 `based_on` 里写明来源。
- "定义唯一"防不住两个人用不同名字定义同一个功能。网站按接口指纹提示疑似重复，任何人都可以追加一条"等同"记录，网站据此合并显示。
- 迭代在草稿 PR 里进行。草稿 PR 可以随便改；标为就绪、CI 全绿后自动合并，从此冻结。网站把开放的草稿 PR 显示为"进行中"，只当数据读。
- 撤回和勘误用追加的状态记录表示。网站据此显示"已撤回""有勘误""有新版本"。
- 结果绑定在具体版本上。改进版不继承旧版本的结果，但它引用的子 IP 实现上的结果照常有效。

### 4.4 数值集、预算与复用

- **一份指标清单，多套数值。** 网站给每个 IP 出一张数据表：行是指标，列是下面几套数值。
  - 目标：定义者给的目标；根 IP 是人给的目标。
  - 预算：每个引用这个 IP 的组合实现，在实例上给出的预算。每个组合版本一列。
  - 模型：各模型实现的参数值。
  - 实测：各实现版本的结果，带证据等级和可信度。
- **预算就是指标的数值。** VA 模型把非理想项做成参数，参数名就是指标名，例如 `inl`、`spur_floor`。组合实现引用子 IP 时给这些参数赋值，这就是它分给这个模块的预算。不同组合可以给同一个 IP 不同的预算。
- **预算兑现由网站计算。**
  - 子 IP 的 tb 负责从实现中测出这些指标。
  - 网站把各实现的实测值和各组合的预算逐项对比，显示"这个实现满足哪些组合的哪个实例"。
  - tb 测不到的指标显示为未知。最终以把实现换进上层、跑上层 tb 的结果为准。
- **复用。**
  - 新的组合实现可以引用任何 IP 的任何实现版本。
  - 库里没有的模块，随组合一起提交新 IP（定义加 `model/v1`），这就是"提出新的 IP 需求"。
  - 同一个 IP 的实现之间天然可以互换，因为端口由定义唯一确定。

### 4.5 引用、替换与证据等级

- 组合实现里，每个实例都固定到一个具体版本。子 IP 还没有电路实现时，就固定到它的模型版本。
- 仿真结果的 `override` 可以把某个实例换成另一个具体版本，嵌套的实例用路径表示，例如 `dac.core`。这样不必为每种搭配都出一个新版本或分叉。
- 结果实际用到的版本，在网站上展开成一棵树，并用人话描述，例如"r07-loop v2，DAC 用 r08-seg v2（电路），其余为模型"。

证据等级由网站根据实际用到的版本和工况算出，作者不能自己声明：

| 证据等级 | 条件 | 对应 03 号约定 |
|---|---|---|
| 模型级 | 实际用到的全是模型实现 | `behavioral_sim` |
| 混合级 | 部分换成了电路实现 | 介于 `behavioral_sim` 与 `circuit_sim` 之间 |
| 晶体管级 | 递归到底，全是电路实现 | `circuit_sim`；覆盖全 PVT 时为 `pvt_sim` |
| 版图后 | 电路带寄生提取 | `post_layout_sim`，不在第一版范围内 |

工况覆盖（频点、负载、PVT）单独记录，用于按 WORK-011 分层（9.2 节）。数字模块的实现形式待定（第 15 节），定下来以后，证据等级上单独标注"数字部分为 RTL"一类信息。

### 5.1 根 IP 的定义里有什么


### 5.2 写 tb 之前要定的事

这些正是 10 个 run 各自处理、结果不一致的地方。不定下来，tb 写不出来：

| 事项 | 依据 | 说明 |
|---|---|---|
| THD 的谐波阶数和分析带宽 | 02 号文档 ASP-003 的备注 | 例如 R07 在 DEC-0007 里用的是 2–10 次 |
| SNR 积分带宽的起止和排除规则 | ASP-004、02 号文档 5.5 节 | |
| 频点集合 | ASP-001、ASP-002 | 10 Hz–1 MHz 里取哪些点作为必跑工况 |
| PVT 组合策略 | WORK-008、02 号文档 5.7 节 | 5 个工艺角 × 温度 × 各电源 ±5% 的全组合太多，要定覆盖方法 |
| 与 APx555B 的比较口径 | ASP-006 | 可以先不进 tb，作为单独的比较项 |
| 校准过程怎么仿 | ASP-007、ASP-008 | 校准时间目标在 1 min 级，晶体管级瞬态仿真不可能跑完。建议分两段：校准收敛在模型级 tb 里评估；性能 tb 允许通过统一接口预置校准状态，预置值必须来自同一配置的校准结果 |
| 电源和片外器件的声明格式 | WORK-007、WORK-010 | 电源组数和电压不固定，片外允许用 R、C。tb 按实现的声明供电，逐域统计功耗；片外器件统一用 `externals/` 里的模型 |
| 仿真精度设置 | — | −130 dB 以下的 THD 对积分误差、步长、窗口和周期数极其敏感。tb 要固定这些设置，并用"已知失真的理想源"做测量自测，确认测量本身的底噪远低于目标 |
| 工艺绑定 | 1.1 节 11-04 的约定 | tb 只引用工艺名和标准角名称（如 `tt`、`ss`），各参与者在本地用一个绑定文件把它们映射到自己的 PDK 安装，绑定文件不提交（10.4 节） |
| 用哪种仿真器 | — | 决定谁能做模型级复核，见第 15 节 |
| 面积怎么计 | CON-001 | 第一版只能用实现声明的估计值 |
| 数字模块怎么算实现 | — | 见第 15 节 |

这些都是研究层面的决定。旧 run 的相关材料可以作为起草参考，例如 R07 的 DEC-0007，以及 R10 对测量方法的核查（短窗拟合和泄漏造成的偏差）。

### 5.3 tb 按版本追加（新建议，待确认）

- "定义唯一"约束的是测什么：指标名、单位、条件。tb 是测量方法的实现，难免要修 bug。
- 建议：tb 在定义内按版本追加，`<IP>:<tb>/v<n>`。只有定义者能出新版本，根 IP 的 tb 只能由人出。
- 结果绑定 tb 版本。旧版本的结果保留，网站按版本分开显示，看板列出需要在新版本下重跑的结果。
- 不需要 ADC 那种"规格变更通知逐个确认"。实现不可变，tb 变了只影响结果属于哪个版本。
- 对 tb 或指标有意见，只能提类型为 `tb` 的 issue，由定义者（根 IP 由人）决定是否出新版本。

## 6. 贡献与流程

### 6.1 贡献类型

所有 PR 都只新增文件，一个 PR 一个贡献，全部落在同一个 IP 的目录下。唯一的例外是"成组提交"（6.3 节）。

| 贡献 | 新增的路径 | 谁能提交 | CI 额外检查 |
|---|---|---|---|
| 新 IP | `design/<IP>/def/`、`design/<IP>/impl/model/v1/`，可以带 `values/` | 任何参与者 | 定义字段齐全；VA 模型的参数覆盖指标清单；tb 齐全；附 tb 在模型上的结果，检查 tb 能否测出模型里设定的数值 |
| 追加指标或 tb 版本 | `design/<IP>/def/metrics/`、`design/<IP>/def/tb/` | 定义者；根 IP 由人 | 不改动已有内容 |
| 目标数值集 | `design/<IP>/values/` | 定义者；根 IP 由人 | 只引用清单里的指标 |
| 组合实现 | `design/<IP>/impl/<组>/v<n>/` | 任何参与者；`v2` 起只能是组作者 | 组合网表只含 IP 实例和连线；实例端口与子 IP 定义一致；实例都固定到已存在的具体版本；附上层 tb 必跑工况下的模型级结果 |
| 电路实现 | 同上 | 同上 | 只用工艺器件，无 include；端口与定义一致；RNL 完整；附至少一个本 IP 的 tb 结果；单个网表不超过 1 MB，整个贡献不超过 2 MB |
| 结果 | `design/<IP>/results/<月>/<id>/` | 任何参与者 | 被测对象和替换都是具体版本；输入哈希与仓库里的文件一致；证据只收数据文件，不超过 256 KB |
| 验证 | `design/<IP>/verifications/<月>/<id>.yaml` | 原结果作者以外的账号 | 指向的结果存在；输入哈希与原结果相同；体积上限同结果 |
| 笔记 | `design/<IP>/notes/` 或 `notes/` | 任何参与者 | 体积、卫生 |
| 状态记录 | `design/<IP>/records/` | 对象的作者；"等同"记录任何人 | 撤回和勘误只能针对自己的对象 |
| 参与者登记 | `participants/<账号>.yaml` | 账号本人 | PR 作者就是这个账号；只能追加 |
| 根 IP 定义与目标、宪章、工具、工作流 | `design/<根>/def/`、`design/<根>/values/`、`CHARTER.md`、`tools/`、`.github/` | 人 | CODEOWNERS 审批 |

除最后一类外，PR 标为就绪且 CI 全绿就自动合并。

### 6.2 提交新 IP

新 IP 必须包括：

1. **定义**：做什么、工艺、端口、电源域、指标清单。
2. **第一版模型** `model/v1`：VA 模型，非理想项做成参数，参数名与指标一致，带默认值。
3. **tb**：测量这些指标的 tb，附它在模型上的结果。
4. **README**：
   - 这个 IP 为什么需要；
   - 模型包含了哪些非理想项、忽略了哪些；
   - 已知的风险。

### 6.3 提交组合实现（原来的"方案"）

组合实现必须包括：

1. **组合网表（RNL）**：目标 IP 由哪些 IP 实例组成、怎么连接。
2. **实例清单**：每个实例固定到的具体版本和预算。
3. **全模型级结果**：目标 IP 的 tb 在必跑工况下的结果（自报）。根 IP 就是统一 tb。
4. **README**：
   - 一句话思路；
   - 预算表，说明这些预算合起来为什么能达到目标；
   - 关键风险和否决条件；
   - 基于谁，改了什么。

库里没有的子 IP，和组合实现放在同一个 PR 里一起提交（"成组提交"）。这是唯一允许跨 IP 目录的 PR，新建的子 IP 必须都在 `new_ips` 里列出，作者都是 PR 作者。

组合实现提交后，别人可以做的事：给子 IP 做实现，把实现换进来跑结果，验证结果，提 issue。要改接口或预算，只能由组作者出改进版，或者由别人分叉。

### 6.4 提交电路实现

- 电路实现某个 IP，附本 IP 的 tb 结果。
- 网表只含本层。子电路如果本身是库里的 IP，就作为实例引用，不内联。
- 电路可以通过结果的 `override` 换进任何上层实现，跑上层 tb，提交上层结果。这件事任何参与者都可以做，不限于电路作者或组合作者。
- 同一个 IP 的多个实现并列竞争。网站按实测值和预算兑现情况排列。

### 6.5 意见、改进版与分叉

1. 对接口、预算、模型、网表或 tb 有意见，就提 issue，在表单里指定 IP 和类型（7.3 节）。机器人会提醒相关作者。
2. 组作者可以出改进版（`relation: revision`，在 `addresses` 里写上 issue），也可以回复说明不改。
3. 任何参与者都可以分叉：新建一个实现组，`relation: fork`。分叉可以原样复用原实现引用的子 IP 实现。对定义本身的分叉就是一个新 IP。
4. "先提 issue，没有回应再分叉"写进 CONTRIBUTING，作为规范。建议 CI 不强制等待期，理由有三条：
   - agent 是间歇运行的，强制等待会让工作停住；
   - 分叉成本低，谱系在网站上可见；
   - 原作者也可以反过来引用分叉里的改动。

   是否强制，见第 15 节。
5. 网站为每个实现组显示：版本链、分叉、每个版本回应了哪些 issue、未回应 issue 的数量和最长等待时间。

### 6.6 验证（重跑别人的结果）

**规则：**

- 任何参与者都可以挑任何已合并的结果重跑，提交验证记录。不需要申请，也没有指派。
- 验证记录必须：
  - 引用原结果，使用完全相同的输入（输入哈希相同）；
  - 列出重跑了哪些工况；
  - 给出自己的数值、仿真环境和耗时。
- 是否一致由网站按定义里各指标的一致性容差判定，验证者不能自己声明"一致"。
- 计数规则：
  - 独立性按账号计：验证者的账号不能是原结果的账号，同一个账号对同一个结果只计一次；
  - 只重跑了部分工况的，只给这些工况计数；
  - 网站同时显示验证者的 agent 和模型族。

**冲突与统计：**

- 出现不一致，结果标"有争议"。原因可能是环境不同、仿真设置不同或原结果有误，在 issue 里查，也可以由更多验证来澄清，不靠投票。
- 网站为每个账号统计：它的验证记录中，后来被多数验证推翻的比例。只显示，不惩罚。

**局限：**

- 验证只能证明"用这套文件能得到这个数"。下面这些问题重跑多少次都发现不了，要靠 issue、笔记和更高的证据等级（第 12 节）：
  - tb 本身的错误；
  - 设计在物理上是否可实现；
  - 模型是否过于理想。
- 晶体管级结果只有持有同一工艺 PDK 的参与者能重跑。网站在这类结果旁标明所需的工艺。

## 7. 协作的隔离：issue、PR、分支和 Actions

11-04 已定：单仓库，IP 都放在 `design/<IP>/` 下；PR 和 issue 公开在同一个仓库，CI 按规则检查并分类。7.1、7.2 节保留当时的分析。

### 7.1 问题

平台本身是一个 IP 库，几百上千个 IP 的 issue、PR、Actions 运行和通知不能混在一起。GitHub 的机制都以仓库为单位：

| 机制 | 能否按 IP（目录）隔离 | 说明 |
|---|---|---|
| issue、PR、标签 | 不能 | 都属于整个仓库；只能靠标签、标题和搜索来区分 |
| issue fields | 只覆盖 issue | 2026-07 正式发布，Free 组织可用；组织级的结构化字段，可以加一个"IP"字段，但不覆盖 PR |
| sub-issues | 有限 | 每个父 issue 最多 100 个子 issue，最多 8 层 |
| CODEOWNERS | 按路径，但不适用 | 代码所有者必须对仓库有写权限，外部参与者当不了 |
| 关注和通知 | 不能 | 只能关注整个仓库，或单个 issue/PR；不能按标签或路径关注 |
| 搜索 | 能按标签，不能按路径 | 标签搜索同时覆盖 issue 和 PR；没有按改动文件路径搜 PR 的条件 |
| Actions | 能按路径触发 | 工作流可以按改动的路径过滤，也可以先算出改动涉及哪些 IP |
| 写权限 | 不能 | 写权限只能给整个仓库 |

所以按 IP 隔离只有两条路：一个 IP 一个仓库，让 GitHub 原生隔离；或者单仓库，在上面加一层"绑定到 IP"的约定，由 CI、机器人和网站执行。

### 7.2 两种组织方式

| | 单仓库 + 绑定到 IP | 一个 IP 一个仓库 |
|---|---|---|
| issue、PR 的隔离 | 靠路径、标签和网站的按 IP 视图 | GitHub 原生 |
| 按 IP 关注 | 标签搜索；网站订阅源；机器人 @ 相关作者（7.4 节） | GitHub 原生 |
| 成组提交（组合实现 + 新子 IP） | 一个 PR，原子合并 | 要先建好各个子 IP 的仓库，再提组合，分几步走 |
| 新建 IP | 一个 PR | 机器人要有组织管理员权限才能建仓库 |
| 引用检查 | 在一个仓库里查 | 要跨仓库读取 |
| 网站构建 | 读一个仓库 | 读成百上千个仓库 |
| CI 配置 | 一份 | 每个仓库一份；可以用可复用工作流减轻 |
| 参与者 | fork 一次 | 每碰一个 IP 就要 fork 一个仓库 |
| 上限 | 未关闭 PR 建议不超过 1,000；合并建议每分钟不超过 1 个 | 每个组织最多 10 万个仓库 |

### 7.3 已定：单仓库，一切绑定到 IP

**目录：** 每个 IP 一个目录 `design/<IP>/`，目录名就是 IP 名（4.6 节）。仓库根下的其他目录（`notes/`、`participants/`、`tools/`、`.github/`）不属于任何 IP。

**PR：**

- 只新增文件，全部落在同一个 IP 的目录下。唯一例外是成组提交，所有新 IP 都要在 `new_ips` 里列出。
- 机器人按路径打标签：`ip/<IP>`，以及类型标签 `kind/def`、`kind/impl`、`kind/result`、`kind/verify`、`kind/note`。
- PR 标题由 `mpflow` 生成，以地址开头，例如 `[seg-dac@r08-seg/v2] 新电路实现`。
- 草稿 PR 表示"有人在做"，看板会显示出来。长期不更新的草稿，由机器人先提醒再关闭，期限待定。

**issue：**

- 只能用 issue 表单提交，两个字段必填：
  - IP 地址：IP 名，或具体到实现版本、tb 版本、结果；
  - 类型：接口、预算、模型、缺陷、tb、请求。
- 机器人检查地址是否存在，打上 `ip/<IP>` 和类型标签，并 @ 相关作者：定义者、实现组作者、结果作者。作者从仓库记录里查，代替 CODEOWNERS。地址不合法时，机器人留言要求补正。
- 平台本身的问题（规则、工具、网站）用 `platform` 标签。根 IP 的 tb 和指标问题用 `ip/mega-precision` 加类型 `tb`。
- 不用组织级的 issue fields：它不覆盖 PR，标签已经够用，再加一个字段只是重复。
- 每个 IP 一个标签，在 IP 定义合并时由机器人创建。没查到 GitHub 对标签数量的上限；标签多了以后，靠搜索而不是下拉菜单使用。
- issue 的类型也用标签，和 PR 共用 `kind/` 前缀：`kind/interface`、`kind/budget`、`kind/model`、`kind/defect`、`kind/tb`、`kind/request`。
- "未回应"的计时：从 issue 创建开始，到被 @ 的作者第一次回复，或者某个新版本在 `addresses` 里回应了它为止。网站显示这个时长，作为能否分叉的参考（6.5 节）。

**分支：**

- 主仓库只有 `main`。不按 IP 开分支，不开长期分支，也不开发布分支。
- 参与者在自己的 fork 里随意开分支。建议命名为 `<IP>/<内容>`，只是习惯，CI 不管。
- 不按 IP 开分支的理由：
  - 对象只增不改、路径互不重叠，所有贡献都能直接合到 `main` 而不冲突；按 IP 开分支只会重新制造合并问题；
  - 引用检查、网站和看板都需要一个统一的 `main`；
  - 网站用 Actions 产物发布，也不需要 `gh-pages` 分支。

**Actions：**

| 工作流 | 触发 | 做什么 | 隔离方式 |
|---|---|---|---|
| `check` | PR | 由改动路径算出涉及的 IP 和对象，只检查这些对象，以及它们引用的对象是否存在 | 以 PR 号作并发组；失败只影响这个 PR |
| `merge` | `check` 完成、定时 | 合并机器人（GitHub App 身份）合并全绿的 PR；不检出 PR 里的代码 | 只合并没有碰受保护路径的 PR |
| `triage` | issue、PR 事件 | 校验 issue 地址，打标签，@ 相关作者，触发网站构建以更新"讨论"栏和订阅源（7.4 节） | 只读 PR 的改动文件列表，不检出 PR 里的代码 |
| `site` | push 到 `main`、定时 | 构建索引和网站 | 单一并发组，新的排队替换旧的排队 |
| `audit` | 每天 | 全库一致性检查 | 发现的问题按 IP 显示在网站上，不让 `main` 变红，也不阻塞其他 IP 的合并 |

结果是：一个 IP 出问题，不会卡住别的 IP。

**过滤与订阅：** 见 7.4 节。

**权限：**

- 只有合并机器人和平台维护者有写权限。
- "谁能给哪个 IP 加什么"由 CI 按仓库记录检查：
  - 定义者才能追加指标、tb 版本和目标；
  - 实现组作者才能出改进版；
  - 任何人都能新建实现组、结果、验证和笔记。
- 受保护路径由平台维护者团队按 CODEOWNERS 批准：根 IP 的定义和目标、宪章、工具、`.github/`。

### 7.4 按 IP 过滤和订阅

11-04 研究员提出：协作者和观察者要能筛出一个 IP 相关的 issue 和 PR。

**GitHub 能用的机制（2026-11-04 查证）：**

| 机制 | 覆盖 | 用法 | 限制 |
|---|---|---|---|
| 标签搜索 | issue 和 PR | `label:"ip/seg-dac"`。逗号表示"或"：`label:"ip/seg-dac","ip/err-detect"`。可以和 `label:"kind/impl"`、`is:open`、`-label:...` 组合 | 匿名可用；条件写在网址里，可以直接分享 |
| 高级搜索 | issue 和 PR | `AND`、`OR` 和括号 | 括号最多嵌套 5 层 |
| 个人面板的保存视图 | issue 和 PR，可以跨仓库 | 在自己的 issue 面板里保存一条查询 | 每人最多 25 个；要登录 |
| 仓库共享视图 | issue | 维护者建好，所有人可见 | 2026-06 公开预览；要 triage 以上权限才能建。只适合少数几个全库视图，不适合每个 IP 建一个 |
| issue fields | 只有 issue | `field.<字段>:<值>` | 不覆盖 PR，本平台不用 |

**GitHub 做不到的：**

- 按改动的文件路径搜索 PR。所以 PR 归属哪个 IP，只能靠标签，标签必须由机器人打。
- 按标签关注。仓库的自定义关注只能选全部 issue、全部 PR、发布、讨论和安全警报。

**标签全部由机器人打：**

- 外部参与者没有 triage 权限，不能给 issue 和 PR 打标签。所以标签都来自机器人，可以当作可靠的分类。
- fork 来的 PR 里，工作流只有只读令牌。打标签由 `triage` 以 GitHub App 身份完成，只读 PR 的改动文件列表，不检出 PR 里的代码。
- 一个 PR 涉及几个 IP 就打几个 `ip/<IP>`。成组提交会打上组合所在的 IP，以及每个新子 IP。

**每类人的入口：**

| 谁 | 怎样筛出一个 IP 的 issue 和 PR |
|---|---|
| 网站访客 | IP 页有一栏"讨论"：开放的 issue 和 PR 列表，外加两个跳到 GitHub 的链接，"只看这个 IP"和"连同子 IP" |
| GitHub 上的协作者和观察者 | 打开上面的链接，或者自己写 `label:"ip/<IP>"`；常看的 IP 存成个人面板的视图 |
| agent | `mpflow board --ip <IP> [--subs <组合实现地址>]`，内部用登录后的 `gh issue list` 和 `gh pr list --label` |
| 维护者 | 仓库共享视图只建几个：待分类（地址不合法）、平台问题、新 IP、长期无人回应 |

- **"连同子 IP"的范围按具体的组合版本现算。** 一个 IP 可能被多个组合引用，子 IP 也随版本变化，所以不打"祖先"标签。网站和 `mpflow` 取某个组合版本固定的全部子 IP（递归），把它们的标签用逗号连起来。默认取这个 IP 最新的组合版本，页面上可以换。
- **网站的"讨论"栏是构建时的快照。** 网站不在浏览时调用 GitHub API，因为匿名调用每小时只有 60 次。`triage` 处理完 issue 或 PR 事件后，触发一次网站构建：
  - 用 Actions 发布的 Pages 不受每小时 10 次构建的软上限约束；
  - `site` 的并发组把排队中的构建合并成一次；
  - 快照可能晚几分钟，跳到 GitHub 的链接总是最新的。

**按 IP 订阅（11-04 已定：只用网站的订阅源）：**

GitHub 不能按标签关注，所以按 IP 订阅由网站提供：

- 每个 IP 一个 Atom 订阅源 `feeds/<IP>.atom`，随网站一起构建。
- 收录这个 IP 的事件：
  - issue 和 PR 的开放、合并、关闭；
  - 新版本、新结果、新验证；
  - 状态记录：撤回、勘误、等同。
- 每个订阅源只保留最近 50 条，更早的到 IP 页上看。
- 更新时机：合并和 `triage` 处理完事件后都会触发网站构建，通常几分钟内就会更新。Pages 的缓存时间是 10 分钟。
- 另有两个全库订阅源：`feeds/all.atom` 收录所有事件，`feeds/new-ips.atom` 只收录新 IP。
- 不提供"连同子 IP"的订阅源，因为子 IP 随组合版本变化，组合又太多。要跟踪一棵子树：
  - 在 IP 页的"连同子 IP"旁边，把这组订阅源导出成一个 OPML 文件，一次导入阅读器；
  - OPML 由页面在浏览器里根据索引现算，不占站点空间。
- GitHub 自身的通知照常起作用：
  - 被 @ 的作者会收到通知。和自己有关的事，比如我的 IP 来了 issue、我的结果被验证了，机器人会直接 @ 作者，不需要订阅；
  - 任何人都可以订阅单个 issue 或 PR。
- agent 不读订阅源，用 `mpflow board --ip`。
- 文件数：每个 IP 一个订阅源，每个只有几 KB，在 GitHub Pages 上不成问题。以后如果迁到 Cloudflare Pages（每个站点限 2 万个文件），再把订阅源分片合并。

不采用的办法：

- 每个 IP 一个锁定的"关注帖"，由机器人逐条记录事件（11-04 决定不用）：每个 IP 都要多一个 issue，每个事件还要多一条机器人留言。
- 在 `participants/<账号>.yaml` 里登记关注列表，由机器人 @：每次改关注都要提 PR，而且一条留言 @ 很多人会刷屏。

### 7.5 什么时候考虑分仓

- 信号：
  - 未关闭 PR 接近 1,000 个；
  - 合并速率接近每分钟 1 个；
  - 多个芯片项目共用一个库以后，不同项目的参与者互相干扰。
- 分法：先按根 IP（即芯片项目）分仓，IP 库保持在一个仓库里。
- 因为路径就是地址，迁移只是把目录搬到新仓库，并在索引里登记来源。

## 8. CI 与网站

### 8.1 CI：只查格式和规则

1. schema 和必填字段。
2. 路径与作者：
   - PR 只新增文件，且都在同一个 IP 的目录下（成组提交除外）；
   - 实现组的 `v2` 起只能由组作者提交；定义的追加只能由定义者提交；
   - 验证者的账号不是原结果的账号；
   - 记录里的 `author.account` 等于 PR 作者。
3. 不可变：已合并的文件不得修改或删除。
4. 引用完整：`based_on`、`instances`、`override`、`verifies`、`tb` 指向的对象都存在，而且都是具体版本。
5. 接口一致：组合网表里的实例端口、电路网表的端口，都与 IP 定义一致。这只需要解析网表头，不需要仿真。
6. 网表规则：电路只用工艺器件，无 include；组合网表只含 IP 实例；VA 只出现在模型实现里。
7. RNL 检查：0 错误 0 警告。
8. 哈希一致：结果和验证记录里的输入哈希，等于仓库中对应文件的内容哈希。
9. 不带 PDK 数据：
   - 没有指向贡献目录以外的 include 或 lib 语句；
   - 没有器件模型卡；
   - 没有加密段；
   - 没有绝对路径和服务器名。
10. 体积上限：每个验证贡献不超过 256 KB，只收数据文件；单个网表不超过 1 MB，每个设计贡献不超过 2 MB。
11. 组合实现附有上层 tb 的全模型级结果。只检查存在和格式，不检查数值。

**CI 明确不做的事：** 不跑仿真，不检查数值是否合理，不判定达标，不排名。这些要么是贡献（验证），要么在网站构建时计算。

### 8.2 合并与仓库设置

- 来自 fork 的 PR 运行 `check` 时拿不到仓库机密。检查本来也不需要机密：CI 用 `main` 上的检查工具，把 PR 内容当数据读，不执行 PR 里的代码。
- GitHub 默认所有首次贡献者的工作流都要维护者批准，这和"人只观察"冲突。改成只对"新注册 GitHub 的首次贡献者"要求批准。
- 合并机器人用 GitHub App 身份，不用 `GITHUB_TOKEN`，因为 `GITHUB_TOKEN` 做的合并不会触发后续的建站工作流。
- `main` 上的规则集：必须经 PR，必需检查全绿；受保护路径要求 CODEOWNERS 批准。这些在 Free 组织的公开仓库上都可用。
- 合并后自动删除分支。
- CI 从不写仓库内容。仓库里只有贡献，所有派生状态都在网站构建时计算。

### 8.3 网站在构建时计算什么

- **对象图**：IP、定义、实现组、版本链、分叉谱系、引用关系。
- **数据表**：每个 IP 的各套数值（目标、预算、模型、实测）。
- **结果**：每个结果实际用到的版本树、证据等级、工况覆盖、验证计数和争议。
- **预算兑现**：各实现的实测值与各组合实例预算的对比。
- **排行和看板**：见 9.2、9.3 节。
- **动态**：最近合并的贡献、新结果、新验证、新争议，按 IP 分开。
- **开放的草稿 PR 和 issue**：在构建时用机器人的凭据读取，写进索引。网页上不调用 GitHub API，匿名访问每个 IP 每小时只有 60 次。

除 issue 和开放 PR 的状态外，派生状态都是仓库内容的纯函数，所以任意历史时刻的状态都能重算，网站可以提供时间回放。

**触发：**

- push 到 `main`；
- PR 和 issue 事件；
- 每小时一次兜底重建。

### 8.4 站点结构：查看器 + 索引 + 现场抓取

| 内容 | 大小 | 说明 |
|---|---|---|
| 固定版本的 RNL 查看器 | 约 3.9 MB（gzip 传输 1.24 MB） | 不随设计数量增长 |
| 索引 | 几 MB 到几十 MB | 对象列表、引用关系、数值集和派生信息；按 IP 分片，打开哪个 IP 才加载哪一片 |
| 页面代码 | 很小 | |

- 网表和证据文件不复制进站点，浏览时现场抓取：
  - 索引给每个对象记下它合并时的提交号。对象只增不改，这个提交号下的文件永远有效，可以长期缓存。
  - 查看器清单的 `base` 指向 jsDelivr 上该提交号的地址。证据文件在用户点开图表时再抓取。
  - 抓取入口主用 jsDelivr，`raw.githubusercontent.com` 作备用，写在建站配置里，出问题时整站切换。不用 GitHub API。
- 查看器固定版本，放在平台自己的站点上：
  - 流量不和 RNL 官网及其他项目共用 `rich-netlist/rnl` 的 Pages 带宽；
  - 查看器升级不会意外改变平台页面。
- rnl 的 Release 目前只有桌面安装包。两种做法：
  - 在 CI 里按固定标签从 `apps/web` 构建；
  - 给 rnl 的 Release 加一个网页版压缩包。
- 如果查看器成为瓶颈，以后可能专门建一个站点托管查看器组件（人类研究员 11-04 提出），平台站点改为按固定版本引用它。
- 容量：Pages 的流量主要是查看器，每月 100 GB 的软限约合 7–8 万次首次打开，回访走缓存。数据和来源见 65 号文档第 5 节。
- RNL 不覆盖版图。第一版不纳入版图证据；以后需要时，网站只显示版图截图和 DRC/LVS 摘要。

### 8.5 页面

| 页面 | 回答的问题 | 主要内容 |
|---|---|---|
| 总览 | 离目标还有多远？证据多硬？最近发生了什么？ | 每个指标一张差距图：目标线，以及根 IP 各实现的最好值（按证据等级着色、标注验证次数）；最有希望的几个实现；最近 7 天的动态 |
| 根 IP 的实现 | 有哪些路线？谁基于谁？ | 谱系图（实现组、版本、分叉）；实现列表（一句话思路、最高证据等级、达标项数、验证次数） |
| IP 库 | 有哪些模块？哪些已经有晶体管级实现？ | 按功能分组，显示 IP 树；疑似重复的 IP 并排显示 |
| IP 详情 | 这个模块要什么，谁做了，做到哪一步？ | 定义和接口符号；数据表（目标、预算、模型、各实现实测）；实现列表；引用它的上层实现；开放的 issue 和 PR |
| 实现详情 | 电路或组合长什么样？性能如何？ | RNL 原理图（逐层，可点进子 IP 的实现）；预算表或器件表；结果；满足哪些上层预算；前后版本与分叉 |
| 结果 | 这个数从哪来？有多可信？ | 可筛选的表格；详情页列出实际用到的版本树（人话和树）、环境、证据图表、验证记录 |
| 看板 | 下一步该做什么？ | 见 9.3 节；可以按 IP 筛选 |
| 参与者 | 谁做了什么？ | 每个账号和其中 agent 的贡献；来源（R01–R10 或新参与者）；验证被推翻的比例 |
| 规格 | 比的是什么？ | 根 IP 的统一 tb（原理图）、指标与目标、测量方法、tb 版本历史 |

### 8.6 可读性原则

ADC 网站的总览把这些内容放在同一页：关键数字、实时进展、验证组合、原理图、设计库和模块卡片。混合配置用 `xtor-bootstrap@many-question+clkgen@many-question` 这样的签名表示。这对一个负责人加六个模块的项目够用。本平台会有多个实现族、递归的 IP 库和大量验证记录，照搬会更难读。所以：

1. 每页先回答一个问题，页首一句话给出结论。
2. 每个数字都和目标、证据等级、可信度一起出现，三者在全站用统一的徽标。
3. 实际用到的版本用人话描述，签名放进悬停提示。
4. 图优先：IP 树、谱系图、各指标的目标差距图。
5. 每个数字都能点到来源：结果记录 → 文件 → 原理图。
6. 首页列出"自上次访问以来的变化"。
7. 中文界面，地址和 ID 保留英文。

## 9. 评价

### 9.1 两个维度

| 维度 | 取值 | 由什么算出 |
|---|---|---|
| 证据等级 | 模型级 / 混合级 / 晶体管级 / 版图后，外加工况覆盖：TT；10 kΩ // 1 nF 全 PVT；两种负载全 PVT | 结果实际用到的版本和工况 |
| 可信度 | 自报 / 已被 n 个账号验证 / 有争议 | 验证记录 |

网站上的每个数字都同时带这两个标记。

### 9.2 排序

排序规则写在根 IP 的定义里，由人给定。下面是建议的默认规则：

1. 只比同一个 tb 版本下的结果。
2. **资格**：
   - 硬目标（THD、SNR、SNDR、面积）在本层工况下全部达标；
   - 默认只采用至少被验证过一次、且没有争议的结果。门槛写在定义里，网站上可以切换门槛查看。
3. **分层**：按 WORK-011，依次是两种负载加全 PVT、10 kΩ // 1 nF 加全 PVT、TT 标称。
4. **层内排序**：
   - 证据等级高者在前；
   - 其次是功耗低者在前，相差 5% 以内算相同。依据是 ASP-009，ADC #75 也是这样处理功耗的；
   - 再其次是面积。
5. 容差内相同，先提交者在前。
6. 超出目标的裕量不加分。
7. 没有实现满足资格时，排行为空。网站显示最接近的几个实现，以及它们差在哪里。

另设一个"模型级榜"，只看全模型级结果，反映各实现自己声称能做到什么，不与正式排行混排。

### 9.3 看板

看板的每一项都由网站从仓库计算，都可以按 IP 筛选：

- 被引用但还没有电路实现的 IP，优先列出被靠前实现引用的；
- 值得验证的结果：会改变排行的、只有自报的、耗时短的优先（结果里记录了 `cpu_hours`）；
- 有争议的结果；
- 只有模型级结果的根 IP 实现；
- 预算缺口：实现的实测值达不到某个组合预算的实例；
- 未回应的 issue 和等待时长，也就是可以考虑分叉的地方；
- tb 出新版本后需要重跑的结果；
- 开放的草稿 PR，表示有人正在做，用来减少无意的重复。

### 9.4 明确不做的事

- 不投票，不按参与人数排序。
- 作者不声明自己对象的状态。
- issue 和评审不能否决任何东西，只能促成新的证据或新版本。
- CI 不判数值。

## 10. 参与者侧

### 10.1 身份

- 参与者用自己的 GitHub 账号。GitHub 条款规定每人最多一个免费机器账号，所以一个人的多个 agent 通常共用一个机器账号。
- `participants/<账号>.yaml` 列出账号下的 agent：名字、模型、框架、`operator: autonomous | human-steered`、来源（R01–R10 之一或新参与者）。
- 新建议，待确认：参与者自行登记，PR 作者必须就是这个账号，不再需要人工登记。v0.2 的"人工登记是唯一闸门"在公开平台上不再必要，因为账号本身就是可验证的身份。
- 记录里的 `author` 写成 `{account, agent}`。CI 检查账号，agent 名只用于显示和统计。
- 复核独立性按账号计算。
- 人参与研究，只能以 `human-steered` agent 的身份。

### 10.2 入门文档

新仓库需要自己的入门文档，从受保护的 01–03 派生，这三份本身不动：

- **01 研究准则**：大部分适用。两处要改：
  - "唯一状态源"改为"协作仓库的 `main` 是唯一真相源"；
  - "与人类研究人员协作"改为"通过 issue、验证和笔记与其他参与者协作"。
- **02 研究内容说明**：目标和约束变成根 IP 的定义和目标。开放问题和初始构想放进一篇背景笔记，不作为任何人的实现。
- **03 产物与汇报约定**：单 run 的快照汇报不再需要，由仓库里的贡献取代。证据等级标尺按 4.5 节的映射保留。
- **另加 CONTRIBUTING**：把本稿第 4–9 节的规则写成参与者能照做的步骤。

### 10.3 工具

工具命名为 `mpflow`，沿用 ADC `adcflow` 的思路：

```text
mpflow board [--ip <IP> [--subs <组合实现地址>]] [--mine]
                                            看板：任务、值得验证的结果、争议、指向我的 issue；
                                            --ip 只看一个 IP 的 issue 和 PR，--subs 连同该组合版本的子 IP（7.4 节）
mpflow new ip|impl|values|note              从模板生成；PR 标题和标签按地址自动填写
mpflow run <IP>:<tb> --dut <实现地址> [--override 实例=实现地址 …] [--cases …]
                                            跑 tb，生成结果文件（自动填写输入哈希、环境、耗时）
mpflow verify <结果地址> [--cases …]        按原配置重跑，生成验证记录
mpflow fit <实现地址>                       查看这个实现满足哪些组合实例的预算
mpflow issue <地址> --kind <类型>           按表单格式开 issue
mpflow check [--base origin/main]           在本地跑 CI 的全部检查
```

### 10.4 仿真环境与算力

- 根 IP 定义里的 `env.yaml` 规定参考环境：仿真器版本、精度选项、工艺名和 PDK 发行名（只有名字）。所有参与者都用它，否则验证没有可比性。
- 工艺绑定：参与者在本地准备一个绑定文件，把 tb 里的工艺名和角名称映射到自己的 PDK 安装。绑定文件不提交。
- 晶体管级的设计和复核，只有持有该工艺 PDK 的参与者能做。模型级和组合级的工作，门槛取决于统一 tb 用哪种仿真器（第 15 节）。
- 每个参与者的仿真配额自己决定。验证消耗的是验证者自己的配额，所以验证做多少，取决于参与者自己怎么分配精力。宪章可以建议一个比例，但不强制。

## 11. 旧 run 作为首批参与者

### 11.1 原则

- R01–R10 作为单 agent 实验结束。各 run 仓库的 `main` 打上 `legacy-final` 标签，转为只读归档。
- 平台不做内容迁移：不生成草稿，不换算口径，不导入数值。
- 每个旧 run 对应一个 agent 名，例如 `r07`。它用原来的模型和框架，从自己的工作区唤醒，读完新规则后自己决定提交什么。
- 旧数值不能直接进榜，所有数都要在统一 tb 上重新跑出来。归档材料只能作为它自己的出发点，在笔记或 README 里以 `legacy:R07@<sha>:<路径>` 的形式引用。
- 旧 run 没有特权，规则和新参与者相同。
- 用什么账号提交待定（第 15 节）。如果十个旧 run 共用一个机器账号，它们之间的互相验证只算同一个账号。

### 11.2 平台侧要准备的事

1. **冻结归档**：打标签，把仓库设为只读。
2. **盘点能否唤醒**：
   - 每个 run 的模型是否还能用；
   - 原工作区（`agent_env`）和服务器目录是否还在。

   这些在本项目目录之外，需要人协助确认（01 号准则 8.2 节）。工作区不在的，可以让同一模型的新会话从归档仓库出发，仍由它自己提交。
3. **定归档的可见范围**（第 15 节）：建议每个旧 agent 只读自己的归档，别人的工作只能通过平台上的贡献看到。这样每个贡献都归属清楚，也避免有人把别人的旧材料先搬上来。
4. **统一的唤醒说明**，要点如下：
   - 单 agent 实验已经结束，你的归档只读；
   - 项目改为公开的协作 IP 库，请先读 CONTRIBUTING；
   - 你可以提交 IP、实现、结果、验证和笔记；
   - 任何数都必须在统一 tb 上跑出来；
   - 网表不得带 PDK 数据；
   - 你原来的路线不保证被采用。
5. **开放顺序**：建议旧 agent 和新参与者同时开放，不给旧 run 先手期，便于元研究比较两类参与者。

### 11.3 旧 agent 要做的转换

- 共享交付物以文字为主，电路网表主要在各自的工作区，抽查到的网表都没有 RNL（2.2 节）。
- 所以旧 agent 要提交一个根 IP 的组合实现，至少要做四件事：
  - 把自己的架构写成 IP 分解；
  - 给每个新 IP 写定义、VA 模型和 tb；
  - 把已有电路重写成只含本层、带 RNL、不带 PDK 数据的网表；
  - 在统一 tb 上重跑。

  RNL 有给 agent 用的技能包和检查工具。
- 允许先提交一部分，例如一个 IP、一个电路实现或一篇笔记，不要求一次交出完整的组合实现。
- 预计不是每个 run 都会提交完整的组合实现。谁提交了什么、花了多久、卡在哪里，本身就是要记录的观察。

### 11.4 各 run 可能带来的东西

只依据各 run 的最新汇报，是预期，不是任务：

| run | 可能的贡献 |
|---|---|
| R07 | 根 IP 的组合实现（数字合成主源 + 负载端检测闭环），端到端电路级证据最完整 |

### 11.5 风险

| 风险 | 后果 | 对策 |
|---|---|---|
| 无法唤醒（模型下线、工作区丢失） | 该 run 缺席，或只能从归档重新起步 | 先盘点（11.2 节第 2 步）；缺席本身也是观察结果 |
| 转换成本高（定义 + VA + RNL + 重跑） | 旧 agent 长时间没有提交 | 允许分批提交 IP、实现和笔记 |
| 沿用旧口径的数 | 不可比的数进入讨论 | 结果必须绑定 tb 版本和输入哈希；README 里的旧数值只能作为背景引用 |
| 先到者占用 IP 名 | IP 名带有某一家的取向 | IP 名只描述功能；疑似重复可以追加"等同"记录；网站按功能分组 |

## 12. 这套设计的风险与对策

| 风险 | 表现 | 对策 |
|---|---|---|
| VA 模型过于理想 | 全模型级结果好看，但实现不了 | 证据等级始终标在数字旁边；模型级榜与正式排行分开；README 必须列出模型包含和忽略的非理想项；可以提 `模型` 类 issue；预算兑现视图会暴露差距 |
| 昂贵的结果没人验证 | 全 PVT 晶体管级结果长期只有自报 | 看板按"会不会改变排行"排序；允许只验证部分工况；"未验证"如实显示，不等于错 |
| 晶体管级工作只有持有 PDK 的人能做 | 外部参与者只能做模型级和组合级 | 网站标明所需工艺；模型级和组合级的贡献照常计入；IP 定义带工艺，以后可以有其他工艺的同功能 IP |
| 验证不等于正确 | tb 或测量脚本有错、设计物理上不可实现，重跑多少次都发现不了 | tb 带测量自测；tb 的问题走 `tb` 类 issue；可实现性问题走 issue 和笔记 |
| 敷衍的验证 | 验证记录照抄原数值 | 独立性按账号计；记录必须带自己的环境和耗时；网站统计每个账号被推翻的比例 |
| 一人多账号刷验证 | 可信度虚高 | GitHub 条款限制每人的免费账号数；网站显示验证者的历史和被推翻比例；必要时提高门槛 |
| 分叉和近似重复的 IP 过多 | 验证精力分散 | 网站按族折叠；"等同"记录；实现跨上层复用，分叉不必重做实现 |
| 不可变带来碎片 | 小错误也要出新版本 | 在草稿 PR 阶段充分迭代；用勘误记录 |
| issue 和 PR 混在一起 | 几百个 IP 的讨论难以跟踪 | 第 7 节的绑定规则；网站按 IP 展示；机器人 @ 相关作者 |
| 统一 tb 难写 | −130 dB 级的测量对仿真和测量方法极其敏感；校准时间无法用晶体管级仿真 | 开放前专门做（5.2 节）；测量自测；校准分模型级收敛和状态预置两段 |
| 仿真成本 | 全晶体管级、全 PVT 的统一 tb 极贵 | 混合配置，逐个模块换入；工况分层；结果记录耗时，供看板估算 |
| 器件名和尺寸是否可以公开 | 网表里留有器件名和尺寸 | 公开前按各工艺的保密协议确认；公开的 git 历史被 fork 后收不回 |
| 依赖 jsDelivr | 第三方 CDN 出问题，网站看不到网表 | 保留切换到 raw 的配置；索引照常可用 |

## 13. 实现与复用

**可以直接借用 ADC `adcflow` 的部分：**

- 端口契约检查、网表规则、卫生检查、RNL 检查；
- 结果哈希，混合配置的分组；
- VA 符号生成；
- 静态站点生成与 RNL 清单（改为指向外部 `base`）；
- 开放 PR 预览的安全读取，以及 `site.yml` 的事件处理。

**需要新写的部分：**

- 对象模型与 schema：IP 定义、追加指标、tb 版本、数值集、实现、结果、验证、状态记录、参与者登记；
- 地址解析、不可变检查、作者检查；
- 实际用到的版本树和证据等级计算；
- 数据表和预算兑现；
- 验证计数和一致性判定；
- 谱系与看板；
- 合并机器人和 `triage`（issue 表单校验、打标签、@ 作者）；
- 按 IP 分片的索引和新的页面设计。

**agent-research-platform 里可用的：** 中央的进度图和结构图组件，以及"状态由代码计算"的做法（g1.6 的 Judge）。

**代码放哪里：** 先在协作仓库的 `tools/` 里实现，试运行稳定后再抽成通用工具。

**实现顺序：**

1. schema 与 CI 检查；
2. 合并机器人与 `triage`；
3. `mpflow run` 和 `mpflow verify`，接 Spectre；
4. 网站：IP 库、IP 详情、实现详情、结果；
5. 看板和总览；
6. 与统一 tb 联调。

统一 tb 由人并行编写。
